# ADR-001: RAGパイプラインの採用

**ステータス:** 承認
**日付:** 2026-05-17

## コンテキスト

本システムはObsidianノートを知識ベースとして活用する学習支援ツールである。ノートの内容にアクセスする手段として、以下の選択肢がある：

1. RAG（チャンク分割 → Embedding → ベクトルDB → 類似度検索）
2. MCP等でLLMがノートを直接読み込む
3. ファイル一覧 + 全文をLLMコンテキストに渡す

ロードマップ生成やクイズ出題の主軸はLLMの体系的知識であり、ノートは補助的な役割である。そのため、RAGが本当に必要かを検討した。

## 決定

RAGパイプラインを採用する。

## 根拠

RAGにより、LLMの汎用知識だけでは実現できない、ユーザー固有の学習体験を提供できる：

1. **クイズ出題の個別化** — ユーザーのノートの表現・例・コードを踏まえた出題が可能になる。「あなたのノートではこう書いてますが、では○○の場合は？」のような問いは、ノートの関連チャンクを検索して初めて成立する。

2. **ノート横断の矛盾・重複検出** — フィードバック生成時に、対象ノートだけでなく関連するチャンクをベクトル検索で引くことで、ノート間の矛盾や重複を検出できる。

3. **解説時のユーザー自身の言葉の引用** — ユーザーがわからないときに、LLMの汎用的な説明に加えて「あなたのノートにはこう書いてあります」と自分の記述を参照として提示できる。

4. **ロードマップへの正確なマッピング** — 新しいノートがロードマップのどの項目に該当するかを、既存チャンクとの類似度で判定できる。

上記1・3は「ユーザー自身の言葉を活用する」という本サービス独自の価値に直結する。MCP等の直接読み込みではノート数が増えた際にコンテキスト制約に当たるため、ベクトル検索による関連チャンクの効率的な取得が必要になる。

## 却下した選択肢

- **MCP / 直接読み込みのみ**: ノート数が少ないうちは機能するが、スケールしない。また、意味的に関連するチャンクの検索はベクトルDBの方が適している。
- **必要になってから導入**: アーキテクチャの根幹に関わるため、後付けはIngestion・エージェント・DB層すべてに影響する。最初から設計に組み込む方が合理的。
