## 機能概要

取り込みパイプライン全体を定期的に実行するスケジューラ。ファイル差分検出から始まり、チャンク分割・タグ付与・Embedding生成・DB格納、さらに後続のロードマップマッピング・フィードバック生成までをバックグラウンドで順次実行する。

## 振る舞い

### 基本動作

設定された間隔（デフォルト: 15分）で以下のパイプラインを実行する。

```
A1: ファイル差分検出
  │
  ▼ 差分なし → 終了
  │
  ▼ 差分あり
削除ファイル → A5: 該当チャンクをChromaDBから削除
  │
新規・変更ファイル（各ファイルについて）:
  │
  ├─ 変更ファイル → A5: 旧チャンクを削除
  │
  ▼
  A2: チャンク分割
  │
  ▼
  A3: LLMタグ付与
  │
  ▼
  A4: Embedding生成
  │
  ▼
  A5: ChromaDB格納
  │
  ▼
  A6: ロードマップマッピング（既存ロードマップがあれば）
  │
  ▼
  A7: フィードバック生成
```

### 実行モード

- バックグラウンドジョブとして順次実行
- 前回のバッチが完了していない場合、新しいバッチは開始しない（重複実行防止）

### 具体例

15分間隔で実行。10:00に実行開始:
```
10:00:00 - ファイル差分検出 → 新規1件、変更2件、削除1件
10:00:01 - 削除ファイルのチャンク削除
10:00:02 - 新規ファイルのチャンク分割・タグ付与・Embedding・格納
10:00:15 - 変更ファイル1のチャンク差し替え
10:00:30 - 変更ファイル2のチャンク差し替え
10:00:45 - ロードマップマッピング・フィードバック生成
10:01:00 - 完了
10:15:00 - 次のバッチ開始
```

## 技術判断

- 定期バッチ方式を採用する理由: Obsidianは自動保存でファイル変更が頻発するため、リアルタイム監視（watchdog）では不必要な処理が多発する。定期バッチなら「書き終わった」状態のファイルをまとめて処理できる
- 実行間隔を設定可能にする理由: pydantic-settingsで間隔を変更可能にし、用途に応じて調整できるようにする

## 境界条件

- 差分がない場合 → パイプラインの後続ステップは実行せず終了
- パイプライン実行中にエラー発生 → エラーをログに記録し、次のファイルの処理に進む（1ファイルの失敗で全体が止まらない）
- 前回のバッチが実行中 → 新しいバッチはスキップする
- アプリケーション起動直後 → 初回バッチを即時実行する（設定間隔を待たない）

## スコープ外

- パイプラインの個別ステップの手動実行
- パイプラインの並列実行（ファイル単位の並列処理）
- リトライ機構（失敗したファイルの再処理は次回バッチで実施）

## 受け入れ基準

- [ ] 設定された間隔で定期的にパイプラインが実行される
- [ ] 差分がない場合、後続ステップが実行されない
- [ ] 1ファイルのエラーで全体が止まらない
- [ ] 前回バッチ実行中は新しいバッチが開始されない
- [ ] 実行間隔がpydantic-settingsで設定変更できる
- [ ] アプリケーション起動時に初回バッチが即時実行される
