# 概要

- この機能が解決する課題:
  チャンク本文から、ロードマップ候補や検索メタデータとして再利用できる大分類レベルのトピックタグを自動付与する。既存タグ一覧を LLM プロンプトへ渡して表記ゆれを抑制し、同一概念に対するタグの増殖を防ぐ。
- 利用者・呼び出し元・前提条件:
  呼び出し元は ingestion 系ユースケースまたはそれに準ずるアプリケーションサービスとする。入力はチャンク分割済みの本文列であり、各チャンクは独立に判定される。既存タグ一覧は呼び出し元が取得して渡す。本機能自身はタグ一覧の永続化や取得を行わない。LLM 呼び出しは `core/llm/` のインターフェース経由、タグ付与プロンプトは `TaggingPromptStrategy` として外部注入されることを前提とする。

# 入出力

- 入力:
  `TaggingBatchInput` を受け取る。
  - `chunks: list[ChunkTaggingInput]`
    タグ付与対象のチャンク一覧。入力順が処理順と結果順になる。
    - `chunk_index: int`
      ファイル内でのチャンク順序。
    - `text: str`
      LLM に渡す本文。Obsidian 内部リンク記法を含む場合でも、その文字列を変更せずに渡す。
  - `existing_tags: list[str]`
    既存タグ一覧。大分類レベルの正式表記候補として扱う。空リスト可。
  - `prompt_strategy: TaggingPromptStrategy`
    `build_prompt(chunk_text: str, existing_tags: list[str]) -> PromptPayload` を提供する戦略インターフェース。プロンプト文面や出力指示はこの戦略に閉じ込める。
  - `llm_client: LlmTagClassifier`
    `classify(prompt: PromptPayload) -> list[str]` を提供する LLM 呼び出しインターフェース。
- 出力:
  入力順を保持した `list[ChunkTaggingResult]` を返す。
  - `chunk_index: int`
    対応する入力チャンクの `chunk_index`。
  - `tags: list[str]`
    そのチャンクに付与されたタグ一覧。重複は除去される。分類困難な場合は空リストを返す。
    `existing_tags` が空でない場合、各要素は必ず `existing_tags` 内の文字列と完全一致する。
- エラー:
  送出する例外の型名と発生条件を定義する。
  実装詳細ではなく、呼び出し元との契約として記述する。
  - `TaggingPromptBuildError`: `prompt_strategy` がプロンプトを構築できない場合
  - `TaggingLlmCallError`: `llm_client` の呼び出しが失敗した場合。タイムアウト、接続失敗、モデル実行失敗を含む
  - `TaggingResponseFormatError`: `llm_client` が返した結果を `list[str]` として解釈できない場合

# 主要ルール

1. チャンク単位の独立判定:
   - 条件:
     `chunks` に 1 件以上のチャンクが含まれる場合。
   - 振る舞い:
     各チャンクを独立にタグ付与し、他チャンクの本文を判定材料に混ぜない。返却順は入力順を保持する。
2. 既存タグ優先:
   - 条件:
     `existing_tags` が 1 件以上ある場合。
   - 振る舞い:
     LLM には既存タグ一覧を候補として提示し、出力タグは既存タグ一覧の完全一致文字列のみを採用する。意味的に近い新規表記は採用しない。
3. 新規タグ生成の許可条件:
   - 条件:
     `existing_tags` が空リストの場合。
   - 振る舞い:
     LLM は新規タグを生成してよい。生成するタグは大分類レベルのトピック名とし、ロードマップ候補としてそのまま表示できる粒度を要求する。
4. 大分類レベルへの丸め:
   - 条件:
     チャンク本文が特定技術の下位概念、API 名、記法、個別機能を主題とする場合。
   - 振る舞い:
     タグは下位概念名ではなく、それを包含する大分類トピックを返す。例えば `ジェネリクス` は `TypeScript`、`useEffect` は `React`、`LEFT JOIN` は `SQL` のように丸める。
5. 複数タグ許容:
   - 条件:
     1 つのチャンクが複数の大分類トピックにまたがる場合。
   - 振る舞い:
     関連する複数タグを返してよい。タグ数の上限は本仕様では設けない。
6. 分類困難時の空リスト:
   - 条件:
     チャンク本文が抽象的すぎる、文脈不足で大分類を特定できない、または既存タグ一覧に適合候補がない場合。
   - 振る舞い:
     例外にはせず、`tags: []` を返す。
7. Obsidian 内部リンクの保持:
   - 条件:
     チャンク本文に `[[リンク先]]` や `[[リンク先|表示名]]` が含まれる場合。
   - 振る舞い:
     LLM に渡す本文から除去・展開・正規化を行わず、入力文字列をそのまま使う。
8. プロンプト戦略の外部注入:
   - 条件:
     タグ付与のプロンプトや出力指示を変更したい場合。
   - 振る舞い:
     本機能は `TaggingPromptStrategy` を呼び出してプロンプトを構築する。ドメインロジックは具体的なプロンプト文面を保持しない。
9. 重複排除と順序:
   - 条件:
     `llm_client` が同一タグを重複して返した場合。
   - 振る舞い:
     重複は先勝ちで除去する。`existing_tags` が空でない場合の最終順序は `existing_tags` に現れる順とし、`existing_tags` が空の場合は LLM の返却順を維持する。

# 境界条件

- ケース:
  `chunks` が空リスト。
  - 振る舞い:
    空リストを返す。LLM は呼び出さない。
  - 理由:
    タグ付与対象が存在しないため。
- ケース:
  `existing_tags` に重複や空文字、前後空白付き文字列が含まれる。
  - 振る舞い:
    プロンプト構築前に trim し、空文字を除外し、先勝ちで一意化した一覧を候補として扱う。
  - 理由:
    候補一覧自体のノイズで表記ゆれが増えるのを防ぐため。
- ケース:
  チャンク本文が空文字または空白のみ。
  - 振る舞い:
    `tags: []` を返す。LLM を呼び出してもよいが、結果は空リストでなければならない。
  - 理由:
    分類根拠が存在しないため。
- ケース:
  `existing_tags` が非空で、LLM が候補外のタグを返した。
  - 振る舞い:
    候補外タグは採用しない。残りに有効タグがなければ `tags: []` を返す。
  - 理由:
    既存タグによる表記統制を最優先するため。
- ケース:
  `existing_tags` が空で、LLM が細かすぎるタグを返した。
  - 振る舞い:
    呼び出し元に返してよいタグは大分類レベルに限る。下位概念しか返せない応答は不正な分類結果として扱い、`TaggingResponseFormatError` ではなく `tags: []` に丸める。
  - 理由:
    本機能の責務は大分類タグ付与であり、粒度が合わない結果をそのまま流すと後続のトピック候補が汚染されるため。
- ケース:
  1 つのチャンクが既存タグの複数候補にまたがる。
  - 振る舞い:
    関連がある全タグを返してよい。1 つに絞る必要はない。
  - 理由:
    チャンク単位の検索やトピック候補生成で複数軸の参照価値があるため。
- ルール間の相互作用:
  1. まず `existing_tags` を正規化し、その結果が空なら「新規タグ生成可」、空でなければ「既存タグ限定」を適用する。
  2. Obsidian 内部リンク保持は、プロンプト戦略適用前の本文前処理より優先する。リンク解決や除去は行わない。
  3. 大分類レベルへの丸めは、複数タグ許容と同時に適用される。複数返す場合でも各タグは大分類でなければならない。
  4. 分類困難時の空リストは、既存タグ優先より後に評価する。既存タグ一覧に近い候補がない場合も新規生成へフォールバックせず空リストにする。

# 非機能・制約

- 性能:
  LLM 呼び出し以外の前処理は、各チャンク本文と既存タグ一覧に対して線形時間で完了すること。入力チャンク順序を変えないこと。
- 可観測性:
  少なくとも `source_path`、`chunk_index`、使用した既存タグ件数、生成タグ件数、空リストになった件数、LLM 呼び出し失敗件数を記録できること。
- 外部依存:
  `core/llm/` の `LlmTagClassifier` インターフェース、およびプロンプト構築用の `TaggingPromptStrategy` インターフェースに依存する。既存タグ一覧の取得元や永続化先には依存しない。

# 技術判断

品質に直結する技術選定や実装方針がある場合は、その判断と理由を書く。

- 判断:
  既存タグが 1 件でもある場合は、新規タグ生成を禁止し既存タグへの正規化を優先する。
  - 理由:
    表記ゆれ抑制が主目的であり、既存候補がある状況で新規生成を許すと `TypeScript` と `TS` のような分裂を防げないため。
- 判断:
  プロンプト文面は `TaggingPromptStrategy` に閉じ込め、tagger 本体は「入力整形」「LLM 呼び出し」「結果正規化」のみを担当する。
  - 理由:
    `core/` 配下の汎用性を保ちつつ、アプリケーションごとの分類観点や出力制約を差し替えられるようにするため。
- 判断:
  分類できないケースは例外ではなく空リストで表現する。
  - 理由:
    「分類不能」は正常系の一種であり、取り込みパイプライン全体を失敗扱いにする理由がないため。

# スコープ外

この機能では扱わないこと、別 issue / 別機能で扱うことを明示する。

- 対応しないこと:
  タグ一覧の保存・統合・リネーム
- 対応しないこと:
  既存タグ一覧の取得元の決定
- 対応しないこと:
  タグ階層構造の導入
- 対応しないこと:
  Obsidian 内部リンク先の解決やノート本文の追加取得
- 対応しないこと:
  中分類・小分類レベルの詳細タクソノミ設計

# 受け入れ基準

検証可能な条件をチェックリスト形式で書く。実装手段ではなく、満たされるべき事実を書く。

- [ ] 既存タグ一覧が非空のとき、返されるタグは既存タグ一覧の完全一致文字列のみに制限される
- [ ] 既存タグ一覧が空のときのみ、新規タグ生成結果を返せる
- [ ] 1 チャンクに対して複数タグを返せる
- [ ] 分類困難なチャンクは例外ではなく空リストになる
- [ ] Obsidian 内部リンク記法を変形せずに LLM へ渡すことが仕様として定義されている
- [ ] プロンプト生成が `TaggingPromptStrategy` の外部注入であることが明記されている
- [ ] 大分類レベルのタグに丸めるルールが定義されている
- [ ] 境界条件とルール間相互作用から、候補外タグや空入力の扱いを一意に判断できる

# テスト観点メモ

各主要ルールに対して最低1つ、各境界条件に対して最低1つの観点を列挙する。
受け入れ基準の各項目が少なくとも1つの観点でカバーされていることを確認する。

- 正常系:
  既存タグ一覧ありで単一タグが既存表記へ正規化されること
- 正常系:
  既存タグ一覧ありで 1 チャンクに複数タグが付与されること
- 正常系:
  既存タグ一覧空で新規タグがそのまま返ること
- 正常系:
  Obsidian 内部リンクを含む本文が無変換で `prompt_strategy` に渡されること
- 正常系:
  `TaggingPromptStrategy` を差し替えても tagger 本体の入出力契約が変わらないこと
- 境界系:
  `chunks=[]` のとき空リストを返し、LLM を呼ばないこと
- 境界系:
  `existing_tags` の重複・空白・空文字が正規化されること
- 境界系:
  候補外タグのみ返された場合に `tags=[]` になること
- 境界系:
  下位概念しか特定できない本文で大分類に丸められない場合、空リストになること
- 境界系:
  空文字チャンクが空リスト扱いになること
- 異常系:
  `prompt_strategy` 失敗時に `TaggingPromptBuildError` が送出されること
- 異常系:
  LLM 呼び出し失敗時に `TaggingLlmCallError` が送出されること
- 異常系:
  `llm_client` が `list[str]` 以外を返した場合に `TaggingResponseFormatError` が送出されること
