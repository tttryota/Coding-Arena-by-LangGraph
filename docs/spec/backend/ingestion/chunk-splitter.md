# 概要

- この機能が解決する課題:
  Markdown ノートを RAG 用の検索単位へ安定して分割し、後続の Embedding 生成で扱える本文チャンク列を生成する。
- 利用者・呼び出し元・前提条件:
  呼び出し元は ingestion 系ユースケースまたはそれに準ずるアプリケーションサービスとする。入力は 1 ファイル分の Markdown 生テキストであり、UTF-8 として読めることを前提とする。トークン計測には `multilingual-e5-large` のトークナイザを利用できることを前提とする。

# 入出力

- 入力:
  `markdown_text: str`
- 出力:
  入力順を保持した `list[Chunk]` を返す。`Chunk` は以下の 2 フィールドを持つ。
  - `text: str`
    分割後本文。H1/H2 の境界見出し行と、ファイル先頭 YAML フロントマターは含めない。H3〜H6 行は本文として含める。チャンク先頭・末尾の空行は除去し、本文内の改行順序は保持する。
  - `headers: str`
    そのチャンクに対応する見出し階層。H1 と H2 のみを対象とし、`" > "` で連結する。H1 のみなら H1 文字列、H2 のみなら H2 文字列、見出しなしなら空文字列。
- エラー:
  - 空ファイル、空白のみ、見出し欠落、閉じていないコードブロックはエラーにしない。
  - `multilingual-e5-large` のトークナイザ取得またはトークン計測に失敗した場合は、呼び出し元が処理失敗を検知できる例外またはエラー結果として返す。

# 具体例

代表的な入力と、それに対して期待される出力をデータ例で示す。
テストケース生成やレビューで曖昧さが出ないよう、入力・出力ともに具体値で書く。

## 例1

- 入力:
  ````markdown
  # TypeScript入門

  TypeScriptの基本を学ぶ。

  ## 型システム
  ````

  ```yaml
  - text: "TypeScriptの基本を学ぶ。"
    headers: "TypeScript入門"

      ### ジェネリクス

      型引数を使う。

      #### 制約

      `extends` を使う。
    headers: "TypeScript入門 > 型システム"
  - text: "async/await を学ぶ。"
    headers: "TypeScript入門 > 非同期処理"
  ```

# 主要ルール

1. H1/H2 境界分割:
   - 条件:
     コードブロック外にある ATX 形式の H1（`# `）または H2（`## `）行を検出した場合。
   - 振る舞い:
     その行を新しいチャンク境界として扱う。境界見出し行自体は `text` に含めず、`headers` の構築にのみ使う。H1 はトップレベルを更新し、H2 は直近の H1 配下のサブ見出しとして扱う。
2. H3〜H6 の本文包含:
   - 条件:
     コードブロック外にある H3〜H6（`### ` 〜 `###### `）行を検出した場合。
   - 振る舞い:
     新しいチャンクは開始せず、見出し行を含めて親チャンクの `text` にそのまま残す。
3. 見出しなし本文:
   - 条件:
     コードブロック外に H1/H2 が 1 つも存在しない場合。
   - 振る舞い:
     本文全体を 1 チャンクとして返す。`headers` は空文字列とする。
4. YAML フロントマター除外:
   - 条件:
     ファイル先頭行が単独の `---` で始まり、その後に閉じ行として単独の `---` が現れる場合。
   - 振る舞い:
     先頭の YAML ブロック全体を本文から除外する。本文処理開始後に現れる `---` は通常テキストとして保持する。先頭 `---` に対応する閉じ行がない場合はフロントマターとして扱わない。
5. コードブロック保護:
   - 条件:
     トリプルバッククォートで開始した fenced code block 内を処理する場合。
   - 振る舞い:
     その内部では `#` を見出しとして解釈しない。コードブロックの途中では再分割しない。閉じ行がない場合はファイル末尾までコードブロックとして扱う。
6. 512 トークン超過時の再分割:
   - 条件:
     ルール 1〜5 を適用した結果の単一チャンクが、`multilingual-e5-large` のトークナイザ計測で 512 トークンを超える場合。ただし対象が単独コードブロック、またはコードブロックを含むため分割するとコードブロックを途中で切断してしまう場合を除く。
   - 振る舞い:
     段落単位で再分割する。段落境界は空行 1 つ以上で区切られた本文ブロックとする。再分割後の各チャンクには元の `headers` を引き継ぐ。
7. 単一段落の上限超過:
   - 条件:
     非コード本文の 1 段落だけで 512 トークンを超え、段落単位では上限内に収まらない場合。
   - 振る舞い:
     その段落に限り、トークナイザ上の 512 トークン境界で機械的に分割する。コードブロック内部にはこのルールを適用しない。
8. 空チャンク抑止:
   - 条件:
     見出しだけで本文が存在しない、または除外・trim 後に `text` が空文字列になる場合。
   - 振る舞い:
     そのチャンクは出力しない。
9. Obsidian 内部リンク保持:
   - 条件:
     `[[リンク先]]`、`[[リンク先|表示名]]` などの Obsidian 内部リンク記法を含む場合。
   - 振る舞い:
     解決や正規化を行わず、入力文字列のまま `text` に残す。

# 境界条件

- ケース:
  空ファイル、または空白・改行のみのファイル。
  - 振る舞い:
    空リストを返す。
  - 理由:
    検索対象として意味のある本文が存在しないため。
- ケース:
  先頭 YAML フロントマターを除外した結果、本文が空になるファイル。
  - 振る舞い:
    空リストを返す。
  - 理由:
    メタ情報のみのファイルはチャンク化対象外とするため。
- ケース:
  H2 が H1 より先に現れるファイル。
  - 振る舞い:
    H2 単独でチャンクを開始し、`headers` は H2 テキストのみとする。
  - 理由:
    H1 がなくても H2 単位で意味のあるセクションを表せるため。
- ケース:
  H1 が複数回現れるファイル。
  - 振る舞い:
    各 H1 を独立したトップレベル境界とし、それ以前の H1/H2 階層は引き継がない。
  - 理由:
    1 ファイルに複数トピックが並ぶケースを分離するため。
- ケース:
  見出しだけで本文がないセクション。
  - 振る舞い:
    空チャンクは生成しない。
  - 理由:
    後続の Embedding 生成と検索結果のノイズを避けるため。
- ケース:
  512 トークンを超えるコードブロック。
  - 振る舞い:
    1 チャンクのまま保持する。512 トークン超過であっても分割しない。
  - 理由:
    コード文脈保護をトークン上限順守より優先する、という要件のため。
- ケース:
  先頭が `---` で始まるが閉じ `---` がないファイル。
  - 振る舞い:
    フロントマターとして除外せず、通常本文として扱う。
  - 理由:
    「ファイル先頭の YAML のみ除外」を満たすには、閉じ区切りまで存在することを YAML フロントマター成立条件とする必要があるため。
- ルール間の相互作用:
  1. フロントマター除外を最優先で適用し、その後に見出し解析とコードブロック判定を行う。
  2. 見出し判定は常にコードブロック外でのみ有効とする。
  3. 512 トークン超過時の再分割は、見出し境界分割後に行う。
  4. 再分割時はコードブロックを分断しないことを優先し、その結果として 512 トークン超のコードブロックは単一チャンクで残す。
  5. 空チャンク抑止は、見出し境界分割と再分割の両方の後に適用する。

# 非機能・制約

- 性能:
  1 ファイルを 1 回の前方走査で見出し境界とコードブロック境界を抽出し、その後に必要なチャンクだけトークン計測する。全文サイズに対して線形時間で処理できること。
- 可観測性:
  少なくとも入力文字数、生成チャンク数、512 トークン超過による再分割回数、コードブロック保護で上限超過を許容したチャンク数を記録できること。
- 外部依存:
  `multilingual-e5-large` のトークナイザ実装。計測基準は XLM-RoBERTa SentencePiece と一致している必要がある。

# 技術判断

品質に直結する技術選定や実装方針がある場合は、その判断と理由を書く。

- 判断:
  段落分割の単位は「空行区切り」を正とし、H3〜H6 見出しも 1 つの段落要素として扱う。
  - 理由:
    Markdown 本文の意味境界として最も安定しており、H3 以下を親チャンクへ含める要件とも両立するため。
- 判断:
  単一段落が 512 トークンを超える場合のみ、トークナイザ境界で強制分割する。
  - 理由:
    要件の「512 トークン超は再分割」を満たしつつ、通常ケースでは段落意味境界を優先できるため。
- 判断:
  `headers` は H1/H2 文字列を `" > "` で連結した単一文字列で返す。
  - 理由:
    後続コンポーネントがそのまま表示・保存しやすく、既存 ingestion 系のメタデータ表現とも整合しやすいため。

# スコープ外

この機能では扱わないこと、別 issue / 別機能で扱うことを明示する。

- 対応しないこと:
  Setext 見出し（`===` / `---`）の見出し解釈。
- 対応しないこと:
  チャンク内容の要約、リンク解決、メタデータ抽出。
- 対応しないこと:
  `~~~` フェンスやインデントコードブロックなど、トリプルバッククォート以外のコードブロック記法の特別扱い。

# 受け入れ基準

- [ ] H1 と H2 のみがチャンク境界として扱われ、H3〜H6 は親チャンク本文に残る
- [ ] H1/H2 の見出し行は `text` に含まれず、`headers` にのみ反映される
- [ ] 見出しなしの本文は 1 チャンク、`headers` は空文字列になる
- [ ] ファイル先頭の有効な YAML フロントマターのみが除外され、本文中の `---` は保持される
- [ ] コードブロック内の見出し記法は無視され、コードブロック途中では分割されない
- [ ] 512 トークンを超える通常本文チャンクは段落単位で再分割される
- [ ] 単一段落だけで 512 トークンを超える通常本文は、512 トークン境界でさらに分割される
- [ ] 512 トークンを超えるコードブロックは分割されず、単一チャンクとして残る
- [ ] 空ファイル、空白のみ、フロントマターのみの入力は空リストになる
- [ ] 見出しだけのセクションから空チャンクが生成されない
- [ ] Obsidian 内部リンク記法が入力文字列のまま `text` に残る
- [ ] 出力チャンク順序が元の本文順と一致する

# テスト観点メモ

各主要ルールに対して最低1つ、各境界条件に対して最低1つの観点を列挙する。
受け入れ基準の各項目が少なくとも1つの観点でカバーされていることを確認する。

- 正常系:
  H1 のみ、H1 + H2、H2 単独、見出しなし本文、H3〜H6 含有本文、Obsidian 内部リンク含有本文をそれぞれ検証する。
- 正常系:
  先頭フロントマター除外後に H2 とコードブロックと本文中 `---` が混在するケースを検証する。
- 正常系:
  300 トークン前後の段落 2 つからなる H2 セクションを用い、段落単位再分割と `headers` 引き継ぎを検証する。
- 境界系:
  空文字列、空白のみ、フロントマターのみの 3 パターンで空リストを検証する。
- 境界系:
  H1 が複数あるケースで H2 の親が直近 H1 に切り替わることを検証する。
- 境界系:
  見出しだけで本文がないセクションがスキップされることを検証する。
- 境界系:
  先頭 `---` に閉じ `---` がないケースで、除外せず本文扱いになることを検証する。
- 境界系:
  閉じていないコードブロックを含むケースで、ファイル末尾までコードブロック扱いになることを検証する。
- 境界系:
  512 トークン超の単一段落が、コードブロック外では 512 トークン境界で分割されることを検証する。
- 境界系:
  512 トークン超のコードブロックが 1 チャンクのまま保持されることを検証する。
- 異常系:
  トークナイザ初期化失敗またはトークン計測失敗時に、呼び出し元が失敗を検知できる形で処理が終了することを検証する。
