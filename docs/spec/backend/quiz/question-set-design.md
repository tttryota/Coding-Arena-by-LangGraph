## 機能概要

セッション開始時に、ロードマップ項目の理解度を確認するための「確認ポイントリスト」を設計する。LLMが項目のtitleとdescriptionから、何を確認すべきかを判断する。問題文自体はここでは作らず、出題ノードが都度生成する。

## 振る舞い

### 基本動作

ロードマップ項目のtitle + descriptionを受け取り、確認ポイントのリストを返す。

各確認ポイントには以下を含む:
- 確認する内容（何を理解しているか確認するか）
- 出題形式（知識のみ / 知識+実践）

### 知識+実践のセット出題

コードで表現できる確認ポイントには、知識問題と実践問題をセットで出題する。概念的なポイントは知識問題のみ。この判断はLLMが行う。

### 確認ポイント数の制約

1項目あたり3〜5個の確認ポイント。知識+実践のセット出題を含めると、1セッション6〜10問程度。深掘りで追加される場合はこれを超えるが、20問を超えた場合は収束に向かう。

### 具体例

入力:
```
title: "ジェネリクスの基本構文と型パラメータ"
description: "TypeScriptのジェネリクスの基本的な構文と、型パラメータの使い方を理解する"
```

出力:
```
確認ポイント:
1. ジェネリクスの概念と必要性（知識のみ）
2. 型パラメータの構文理解（知識+実践）
3. 明示的型指定と型推論の違い（知識のみ）
4. ジェネリクスを使った関数定義（知識+実践）
5. any型との比較によるジェネリクスの存在意義（知識のみ）
```

→ 知識問題5問 + 実践問題2問 = 計7問（深掘りなしの場合）

## 技術判断

- 問題文ではなく確認ポイントを設計する理由: 問題文は前の問答の文脈を踏まえて出題ノードが都度生成する。事前に問題文を作ると文脈を無視した出題になる
- 知識+実践のセット出題を設ける理由: 概念を説明できてもコードに落とせないケースがある。生成AI時代にアウトプット力を鍛える場として両方を確認する
- 確認ポイント数を3〜5個に制約する理由: ロードマップ側で具体項目の粒度を制御することで、問題数の肥大化を防ぐ

## 境界条件

- descriptionが空 → titleのみから確認ポイントを設計する
- 概念的な項目でコード実践が不適切（例: 「プログラミングパラダイムの比較」） → 全て知識のみ
- まとめテスト（中枠・大枠） → 配下の具体項目から重要な確認ポイントを抜粋。問題は絞り気味にする

## スコープ外

- 確認ポイントの手動編集
- 問題のテンプレート管理
- 難易度の段階設定

## 受け入れ基準

- [ ] ロードマップ項目から確認ポイントリストが生成される
- [ ] 各確認ポイントに出題形式（知識のみ / 知識+実践）が指定される
- [ ] 確認ポイント数が3〜5個の範囲で生成される
- [ ] コードで表現できるポイントに実践問題がセットされる
- [ ] まとめテスト時は問題が絞り気味に設計される
