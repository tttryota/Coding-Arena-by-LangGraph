## 議題2: サービスの全体像 — ユーザーは何ができるか

### 背景

バックエンドの機能を決める前に、ユーザーがこのサービスで何をできるのかを整理する。
開発計画書から読み取れるサービス像を提示するので、過不足を確認したい。

### 決定事項

#### このサービスは何か

様々なソース（動画・書籍・記事等）で学んだことをObsidianに文書化し、LLMが体系的に整理・理解度チェック・学習支援してくれる個人用学習支援ツール。

#### ユーザーができること

#### 前提制約

- 取り込み対象はVault内の特定パス配下に限定（例: `/study`）
- 対象パスは設定で指定する（汎用基盤として他用途でも再利用可能にするため）

**A. 知識ベースの構築（受動的）**
- 設定された対象パス配下にノートを書くだけで、システムが自動的に取り込む
- 取り込み時にLLMがフィードバックを生成:
  - どのロードマップに反映されたか
  - 内容の正確性チェック
  - 不足している観点の改善提案
- フィードバックは蓄積され、ユーザーが好きなタイミングで確認（未確認フィードバック一覧）
- 確認済みフィードバックの遡りはv1スコープ外

**B. ロードマップ生成（ユーザー起点）**
- システムがノート群から「この人は何を勉強しているか」を分析し、トピック候補を提案
- ユーザーがトピックを選択
- LLMがそのトピックのロードマップ（大枠→中枠→具体）を非同期生成
- ノートでカバー済みの項目 / 未着手の項目を可視化

**C. クイズセッション（メイン体験）**
- ロードマップの項目を選択して開始（未着手 or 復習したい項目）
- 回答形式は2種類:
  - 文章で回答（概念の理解確認）
  - コードで回答（実装力の確認）
- 詳細で具体的な問題が多数提示される
- AIが理解度を評価しフィードバック
- AIが自動で深掘り質問 / ユーザー起点の深掘りも可能
- 前提知識の遡り確認（最大2段）
- わからなければLLMに解説を依頼できる
- セッション終了時にサマリー生成、結果がロードマップの進捗に反映

**D. 学習状況の把握（参照系）**
- ロードマップ × クイズ回答精度 = 各項目の進捗表示
- 弱点（insufficient/partial）の一覧
- 未着手項目 = 次にやるべきことの示唆
- フィードバック一覧は取り込み日時付きで、フロントエンドで日付グルーピング等の表示が可能
  - バックエンドは汎用的な取得API（日付範囲フィルタ、未確認フィルタ等）を提供

## 議題3: ユーザー体験の具体化 — 各体験の詳細フロー

### 背景

議題2で確定した体験について、ユーザー視点での操作フローを具体化する。
「ユーザーが何をしたら、何が起きるか」を明確にし、バックエンドに必要な機能を導出する土台とする。

### 技術スタック変更

- LLM: ~~Qwen2.5-32B（Ollama経由ローカル）~~ → Codex（app-server経由）
- Embedding: multilingual-e5-large（ローカル）維持
- ファイル検知: ~~watchdog（リアルタイム）~~ → 定期バッチ（10〜30分間隔）

### 体験A: 知識ベースの構築 — 決定事項

```
定期バッチ起動（10〜30分間隔）
  │
  ▼ 同期（軽量）
対象パス配下のファイル差分検出（mtime比較）
  - 新規: 前回になかったファイル → 取り込み
  - 変更: mtimeが変わったファイル → チャンク丸ごと作り直し
  - 削除: なくなったファイル → 対応チャンク削除
  │
  ▼ 同期（CPU処理）
チャンク分割
  │
  ▼ 非同期（API呼び出し）
LLMタグ付与
  │
  ▼ 非同期（ローカル推論）
Embedding生成
  │
  ▼ 同期（DB書き込み）
ベクトルDB格納
  │
  ▼ 非同期（API呼び出し）
ロードマップへのマッピング（既存ロードマップがあれば）
  │
  ▼ 非同期（API呼び出し）
フィードバック生成（反映先・正確性・改善提案）→ DB蓄積
```

- バッチ全体をバックグラウンドジョブとして順次実行
- 変更ファイルはチャンク丸ごと作り直し（API呼び出しコストは許容）
- Ollama / watchdog は不要

### ストレージ構成（先行決定）

- **ChromaDB** — チャンク + Embedding（ベクトル検索用）
- **RDB（SQLite）** — ロードマップ、フィードバック、クイズ結果など構造化データ

### 体験B: ロードマップ生成 — 決定事項

```
1. ユーザーがトピック一覧を取得（タグ集約API）
2. トピックを選択
3. LLMがロードマップを非同期で全生成（大枠→中枠→具体、すべて一括）
4. 既存チャンクを各項目にマッピング（カバー済み/未着手を判定）
5. ロードマップをRDB（SQLite）にフラットなレコードで永続化
```

- ロードマップは初回で具体レベルまで全生成（ユーザーに全体像・ゴールを見せる）
- 内容の精査はユーザーに委ねる。項目を指定してLLMに再生成を依頼できる
- 新しいノートが取り込まれた際は、既存項目へのマッピングのみ（構造は変えない）
- クイズセッション終了時にLLMが結果を分析し、ロードマップ改善提案をDBに蓄積（フィードバックと同じ非同期パターン）
  - 項目の細分化提案
  - 前提知識の追加提案
  - ユーザーが確認・承認/却下

### 体験C: クイズセッション — 決定事項

```
1. ユーザーがロードマップから出題範囲を選択
2. LLMが問題セットを設計し、予定問題数（理論値）を提示
3. 出題 → 回答（文章 or コード）→ 評価・フィードバック
4. 回答に応じて深掘り・解説・前提知識の遡りが動的に発生（予定問題数も増減）
5. 問題セット完了 → セッション終了
6. サマリー生成 → ロードマップ進捗に反映
```

**出題範囲の粒度:**
- 具体項目（メイン）— しっかり理解度チェック。進捗管理の単位
- 中枠（まとめテスト）— 配下の具体を横断、問題は絞り気味
- 大枠（まとめテスト）— 全体の理解を問う、さらに絞り気味
- 大枠選択時は中枠の絞り込みを促す

**回答形式:**
- 文章（概念の理解確認）
- コード（実装力の確認）

**セッション中の機能:**
- わからなければLLMに解説を依頼できる
- AI自動の深掘り / ユーザー起点の深掘り
- 前提知識の遡り確認（最大2段）

**進捗管理:**
- 進捗は具体項目のみが持つ（insufficient / partial / sufficient）
- 中枠・大枠の進捗は配下の具体項目から算出
- まとめテスト（中枠・大枠）の結果は記録のみ（実施日時・正答率等）、具体項目の進捗には影響しない

### 体験D: 学習状況の把握 — 決定事項

**D-1. ロードマップ進捗**
- 具体項目の判定状況（insufficient / partial / sufficient）から算出
- 中枠・大枠の進捗は配下から集約

**D-2. 弱点分析**
- insufficient/partialが多い分野の傾向分析
- 上位レベルの示唆（例:「型システム全般が弱い」）

**D-3. 反復学習リマインド**
- 前回クイズから一定期間経過した項目を検出し通知
- 定期バッチで検出 → DBに蓄積（フィードバックと同じ非同期パターン）

**D-4. フィードバック一覧**
- 取り込み時フィードバック + ロードマップ改善提案
- 取り込み日時付き、汎用取得API（日付範囲・未確認フィルタ等）

**D-5. まとめテスト結果**
- 過去の中枠・大枠テストの正答率等を参照可能

## 議題5: 機能グループの分類

### 決定事項

| グループ | 機能 | 性質 |
|---------|------|------|
| **ingestion** | A1〜A5, A7, A8, D4 | 汎用基盤 |
| **roadmap** | B1〜B5, D1, D2 | 学習支援固有 |
| **quiz** | C1〜C9, D5 | 学習支援固有 |
| **infra** | X1〜X5 | 汎用基盤 |

- DDDアーキテクチャで整理する
- 元の `agents/` → `quiz/`（LangGraphは内部実装）
- `api/` は独立グループではなく各ドメインがAPIを公開
- `db/` → `infra/` に統合
- **analyticsグループは廃止**。各機能をingestion/roadmap/quizに再配置:
  - フィードバック生成・一覧(A7, D4) → ingestion
  - 進捗集計・弱点分析(D1, D2) → roadmap（roadmap-retrievalに包含）
  - まとめテスト結果(D5) → quiz
  - 反復学習リマインド(D3) → フロント側で算出（バックエンド不要）

## 議題6: 技術的な設計判断

### 決定事項

#### DDD + パッケージ構成

```
backend/
├── core/                      # 汎用基盤（別リポジトリに切り出し可能）
│   ├── ingestion/             #   取り込みパイプライン（差分検出・チャンク分割・タグ付与）
│   ├── llm/                   #   LLMクライアント（Codex app-server）
│   ├── embedding/             #   Embeddingクライアント（multilingual-e5-large）
│   ├── vectordb/              #   ベクトルDB操作（ChromaDB）
│   └── rag/                   #   RAG検索
│
├── domain/                    # 学習支援固有ドメイン
│   ├── roadmap/               #   ロードマップ管理
│   ├── quiz/                  #   クイズセッション（LangGraphは内部実装）
│   └── analytics/             #   学習分析
│
├── application/               # ユースケース層
│   ├── roadmap/
│   ├── quiz/
│   └── analytics/
│
├── infrastructure/            # インフラ層（学習支援固有の永続化）
│   └── rdb/                   #   SQLite（ロードマップ・クイズ結果・フィードバック等）
│
└── presentation/              # プレゼンテーション層
    └── api/                   #   FastAPIエンドポイント
```

- `core/` は学習支援に一切依存しない汎用パッケージ。他用途（進捗管理・企画等）にも再利用可能
- タグ付与のプロンプトやチャンク分割戦略は設定/ストラテジーパターンで注入可能にする
- `domain/` が `core/` を利用する形で依存方向を明確に

#### ストレージ

- **ChromaDB** — チャンク + Embedding（`core/vectordb/` が管理）
- **SQLite** — ロードマップ・フィードバック・クイズ結果等の構造化データ（`infrastructure/rdb/` が管理）

#### セッション管理

（議題3体験Cで決定済み。LangGraphのステートとしてquizドメイン内で管理）

#### プロンプト管理

（具体仕様書で決める）

#### 開発基盤

| 項目 | 決定 |
|------|------|
| 言語 | Python 3.12 |
| 依存管理 | uv |
| API | FastAPI |
| DB ORM | SQLAlchemy + Alembic |
| バリデーション | Pydantic |
| ベクトルDB | ChromaDB |
| Embedding | multilingual-e5-large（ローカル） |

## 議題7: 大枠仕様書に記載するスコープ

## 議題9: データ構造の設計

### 背景

具体仕様書が「どのテーブルにどう書くか」を前提にするため、先にデータ構造を決める必要がある。

### 9-1. Chunk（ChromaDB）

ChromaDBに格納するチャンクのメタデータ構造。

| フィールド | 型 | 説明 |
|-----------|-----|------|
| id | string | チャンクの一意識別子 |
| content | string | チャンク本文（Markdownテキスト） |
| embedding | vector | multilingual-e5-largeによるベクトル |
| source_path | string | 元ファイルのパス（Vault相対） |
| chunk_index | int | ファイル内でのチャンク順序 |
| headers | string | 見出し階層（例: "TypeScript > 型システム > ジェネリクス"） |
| tags | list[string] | LLMが付与したタグ |
| created_at | datetime | 取り込み日時 |
| updated_at | datetime | 最終更新日時 |

### 決定事項

- idは `source_path + "_" + chunk_index`（例: `study/typescript/generics.md_0`）。ナチュラルキー
- ファイル更新時は `source_path` でフィルタして全削除 → 再挿入
- 上記メタデータ構造で確定

---

### 9-2. RoadmapItem（SQLite）

ロードマップの項目。フラットなレコードで階層を表現する。

### 決定事項

| カラム | 型 | 説明 |
|--------|-----|------|
| id | UUID | 主キー |
| roadmap_id | UUID | どのロードマップに属するか（トピックごとに別ロードマップ） |
| parent_id | UUID / null | 親項目のID（大枠はnull） |
| level | string | "major" / "middle" / "detail" |
| title | string | 項目名 |
| description | string | LLM生成の説明文。クイズ出題のコンテキストにも使用 |
| order | int | 同階層内での表示順 |
| score | int | 0〜100。ラベル変換はアプリケーション層（閾値は設定で変更可能） |
| last_quiz_at | datetime / null | 最後にクイズを実施した日時 |
| created_at | datetime | 作成日時 |
| updated_at | datetime | 更新日時 |

- 階層構造はparent_id方式（ADR-002参照）
- scoreのインターフェース: QuizAnswer.score (int 0〜100) → 集約 → RoadmapItem.score (int 0〜100)
- ラベル変換の閾値（0〜25: not_started相当, 26〜50: insufficient, 51〜75: partial, 76〜100: sufficient）は設定で変更可能
- 集約ロジックの詳細は具体仕様書（progress-update.md）で定義

## 議題10: Ingestion具体仕様の議論

### chunk-splitter — 決定事項

- H1〜H2で分割。H3以下は親チャンクに含める
- 512トークン超のチャンクは段落単位で再分割（ADR-003参照）
- コードブロック（```内）は分割しない
- フロントマターは付与しない前提なので無視
- Obsidianの内部リンク（`[[]]`）はテキストとしてそのまま含める

### tagger — 決定事項

- 大分類レベルのトピックタグのみ（"TypeScript", "Docker", "ネットワーク"等）
- 用途: トピック一覧取得（B1）のトピック候補 + ロードマップマッピング（A6）でロードマップの絞り込み
- 具体項目へのマッピングはタグで対象ロードマップを特定した後、LLMが判定
- 既存タグ一覧をプロンプトに含めて表記ゆれを防ぐ
- プロンプトはストラテジーパターンで注入（core/の汎用性を保つ）
