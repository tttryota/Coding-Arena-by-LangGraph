# 仕様書の書き方ガイド

## 原則

**コードを読めばわかることは書かない。**

仕様書はコードの上位概念を記述する文書であり、実装の詳細を複製する場所ではない。
コードと仕様書の二重管理は必ず乖離し、負債になる。

## 書くべきもの

| 項目 | 説明 | 例 |
|------|------|-----|
| 動機・背景 | なぜこの機能が必要か | 「RAG パイプラインの最初のステップとして、メタデータを分離する必要がある」 |
| 外部から見た振る舞い | 入力→出力の期待を自然言語で | 「Markdown テキストを受け取り、見出しの一覧と目次テキストを返す」 |
| 境界条件の判断 | エッジケースでどう振る舞うか、なぜそう決めたか | 「空入力は空を返す（エラーにしない）。利用側でのガード不要にするため」 |
| 非機能要件 | パフォーマンス、セキュリティ等の制約 | 「100KB 以上のファイルは処理対象外とする」 |
| スコープ外の明示 | やらないことの定義 | 「Setext 形式の見出しは対応しない」 |
| 技術判断と理由 | 品質に直結する選定の根拠 | 「GitHub 風スラッグを採用。主要 Markdown 環境との互換性のため」 |

## 書くべきでないもの

| 項目 | 理由 |
|------|------|
| 関数シグネチャの詳細 | コードを読めばわかる。変更時に追従できない |
| データ構造のフィールド定義 | 同上 |
| 実装アルゴリズムの詳細 | 同上 |
| 変更履歴 | ADR（Architecture Decision Records）として別ファイルで管理する |

## テンプレートの使い方

`TEMPLATE.md` を複製し、各セクションを埋める。

- `status` は `draft` → `in_review` → `approved` の順に進める
- `approved` になるまでハーネスの impl フローは実行できない
- 承認後の変更は ADR に記録し、仕様書本体は「現在の正」のみを保持する

## 受け入れ基準の書き方

受け入れ基準は「何が成り立てば OK か」をチェックリスト形式で書く。
実装方法ではなく、検証可能な条件を記述する。

良い例:
- `[ ]` 空のテキストを渡すと空の結果が返る
- `[ ]` コードブロック内の見出し記法は無視される

悪い例:
- `[ ]` `re.findall` で見出しを抽出する ← 実装手段
- `[ ]` `Heading` dataclass を返す ← データ構造名

## テストケース文書の書き方

テストケース文書は impl フェーズでの pytest コード生成の元になる。
LLM がテストコードを生成する際の入力であるため、曖昧さが品質に直結する。

### 粒度のルール

1テストケース = 1つの検証可能な振る舞い。「AとBとCが正しい」を1件にまとめない。

悪い例:
```
11. 日本語を含む見出しのスラッグが正しく生成される
```
→ LLM が「ひらがな 1 例で十分」と判断し、カタカナ・漢字がテストされない

良い例:
```
11. ひらがなの見出し（例: はじめに）のスラッグが保持される
12. カタカナの見出し（例: セットアップ）のスラッグが保持される
13. 漢字の見出し（例: 設定方法）のスラッグが保持される
```

### テストの種類と検証焦点

全テストで全フィールドを検証する必要はない。テストの種類ごとに焦点を定義し、何を検証すべきかを明示する。

| テストの種類 | 検証焦点 | 例 |
|------------|---------|-----|
| 基本動作 | 全フィールド | 単一入力 → 全出力フィールドが正しい |
| フィルタ/除外 | 含まれる/含まれない | 除外対象が結果に含まれないこと |
| 変換ロジック | 変換結果の正確性 | 変換前→変換後の値が正しい |
| 出力形式 | 出力の構造 | インデント、フォーマットが正しい |
| ハッピーパス | 全機能の統合 | 仕様書の具体例を入力とし、全フィールドを検証 |

### 検証対象の明示

返り値が複数のフィールドを持つ場合、テストの焦点に応じて検証すべきフィールドを明記する。

悪い例:
```
1. 空文字列を渡すと空の目次が返る
```
→ LLM が一部のフィールドしか検証しない可能性がある

良い例:
```
1. 空文字列を渡すと、見出し一覧が空リストで、目次テキストが空文字列で返る
```

### ハッピーパスの統合テスト

仕様書の具体例セクションの入出力をそのまま使い、全フィールドを検証するテストを1件含める。
個別テストが各観点を検証し、ハッピーパスが全機能の連携動作を検証する。
あくまでユニットテストの範囲（単一関数の呼び出し）であり、モジュール間の結合テストではない。

### 具体例の記載

テストケースに具体的な入力→出力の例を含めると、LLM が正確なテストを生成しやすい。
仕様書の具体例セクションと一致させること。
